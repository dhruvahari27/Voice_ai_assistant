# Decision log

Short records of choices that shape the codebase, newest first: what was decided, why, and what would make us revisit it.

## 2026-10-13: Embedded Postgres by default, no Docker, no Redis

**Decision:** default to PGlite (Postgres compiled to WebAssembly, running inside Node) stored in `apps/api/.data`; a real Postgres via `DATABASE_URL` in production. Jobs are rows in Postgres instead of a Redis queue.

**Why:** Docker Desktop wouldn't start on the first development laptop, which blocked everything. PGlite is real Postgres, so the exclusion constraint, `btree_gist`, `pg_trgm` and `FOR UPDATE SKIP LOCKED` all work, and the same migrations and tests run on both. Dropping Redis removes a moving part; at a few thousand jobs a day, Postgres is plenty.

**Revisit if:** job volume grows into the hundreds per second, or several API instances need a shared rate limiter.

## 2026-10-13: One receptionist brain in Node; the Python agent only handles audio

**Decision:** the dialogue manager and all tools live in the Node API. The Python LiveKit agent overrides `llm_node` to send each caller utterance to `POST /api/v1/agent/calls/:id/turns` and speaks the reply.

**Why:** web and phone calls behave identically and are tested once. Booking rules can't drift between two codebases.

**Trade-off:** one extra HTTP hop per turn (a few ms inside the same region).

## 2026-10-13: A deterministic rules engine first, LLM optional

**Decision:** the default receptionist is rule-based (intent + entity extraction for English/Hinglish/Hindi and a small state machine). An OpenAI-compatible LLM can be switched on; it uses the same tools and falls back to the rules engine on errors.

**Why:** it works with no keys and no cost, is fully testable, and is predictable on the narrow job of booking. The LLM handles open-ended phrasing better; the server-side checks make it safe either way.

**Revisit if:** pilot transcripts show many "didn't understand" turns that an LLM would have handled.

## 2026-10-13: The server checks the caller's "yes"

**Decision:** before an agent-initiated booking, change or cancellation, the API reads the caller's latest turn from the transcript and requires it to be affirmative.

**Why:** a prompt is not a guarantee. A test uses a fake model that tries to book without asking; the server refuses.

## 2026-10-12: Drizzle ORM instead of Prisma

**Decision:** Drizzle with plain SQL migrations generated by `drizzle-kit`, plus hand-written SQL for constraints.

**Why:** Prisma needs a native engine binary downloaded at install time, which failed in a restricted environment. Drizzle is plain TypeScript, works with both `pg` and PGlite, and its SQL migrations are easy to hand-edit for the exclusion constraint.

## 2026-10-12: Postgres is the only source of truth

**Decision:** bookings live in Postgres. A calendar (Google Calendar etc.), if added, is a one-way mirror.

**Why:** two writable sources kept in sync by webhooks create race conditions. One source plus a database constraint gives a guarantee instead of a best effort.

## 2026-10-12: The Node API owns every write

**Decision:** nothing but the API writes business data. The receptionist acts only through narrow tools.

**Why:** validation, policy, confirmation, idempotency and audit live in one place. The LLM interprets; the backend owns truth.
